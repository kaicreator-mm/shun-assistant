## 3. Reuse evidence and not-yet-proven matters

- `packages/authorization/src/controller.ts` exports `ActionController.authorizePlan` and `authorizeEffect`. Authorization capability exists; composing it with K is **NOT_RUN**.
- `packages/resolver/src/planner-seam.ts` exposes typed proposal handling, and `packages/llm-remote/src/planner-port.ts` supplies remote planner adaptation. Composition through genuine model response + separate human approval is not yet v0.2 closed.
- `apps/control-api/src/server.ts` exposes system-inventory/diagnosis and cloud/Recipe routes; routes alone are not an accepted end-user journey.
- DomainHarness v0.10.3's neutral `dh.llm.generate/1`, selectable OpenAI-compatible and Anthropic C/Host are **confirmed contract reuse**; Shun P0 selects OpenAI-compatible DeepSeek only unless Product extends it. Endpoint/key/disclosure/cost authority stays in Shun's trusted Host, and the physical consumer path remains unqualified until tested.
- Frozen Guided Journey `step.spec/step.outcome/next-step.request/next-step.decision/llm.advisory` + [offline example](https://github.com/kaicreator-mm/domain-harness/blob/version/v0.10.3/examples/v0103-guided-journey/README.md) support one trusted fact-based step at a time, NOT an arbitrary generated form renderer or permission issuer; Shun owns real UI step/state wiring.
- Selected Meta feedback plus public Host `runMetaFeedbackWorkflow` + [external consumer example](https://github.com/kaicreator-mm/domain-harness/blob/version/v0.10.3/examples/v0103-meta-reuse/README.md) are **confirmed reuse**: bounded candidate validation, shadow and synthetic-operator future BUILD demonstration. Actual human approval, production SQLite persistence, auto promotion, and Shun user-feedback integration are NOT yet proved.
- Two distinct feedback routes: (a) opt-in **Shun task-quality feedback** into domain Meta candidates, (b) **SDK bug/usage feedback** to DomainHarness Issues with redacted reproducible evidence and explicit user permission. Never automatically publish raw user data or a Claim/Token/Prompt.

## 4. L1 risk and materiality

| Concern | Risk | Required Product disposition before L2 |
| --- | --- | --- |
| Double effect authority / Journal | P0 | Single K effect authority after migration; own adapter/transition rollback without broad rewrite |
| Windows user consent & elevation | P0 | Explicit Shun Host authorization remains independent of K permit, both necessary |
| LLM privacy & cost | P0 | No unauthorized disclosure/duplicate send; no zero-effect inference from UNKNOWN |
| Data / Recipe identity | P1 | Durable mapping, migration rollback, protected legacy receipts/unknown state |
| Public SDK distribution/qualification | P1 | v0.10.3 Product/Contract/L2 frozen; use exact version-branch source for development and clean Node24 consumer; finalized package SHA/RQ required before release, not a prerequisite for Product/L2 design |
| Migration maintenance cost / time | P1 | Real K responsibilities displaced, new adapter complexity vs KEEP baseline; do not trade user functionality for cosmetic structure |
| Windows supported OS / packaging | P1 | Physical Windows Home/Pro scope and authenticated first-stage provenance must be tested |
| Guided form step/outcome provenance | P1 | Render one frozen-schema step from trusted Host observation; bounded LLM advisory never gains action authority |
| Meta/feedback promotion authority | P1 | Real user feedback is redacted & source-bound; candidate/Shadow not auto-approved; explicit future BUILD checkpoint |
| Fancy generic UI/agent engine | Deferred | Outside migration value case unless formal later Product amendment |
