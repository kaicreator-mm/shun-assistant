## 1. Executive architecture decision

Shun v0.1 is a **local-first TypeScript/Node control plane** with explicit ports around planning, durable workflow coordination, provider/environment resolution, side-effect authorization, execution, verification, and lifecycle state.

The core invariant is:

```text
User Goal / Known Trigger
  ↓
Intent Normalization
  ├─ deterministic exact trigger / known parameters when possible
  └─ PlannerPort interpretation only when needed (proposal, non-authoritative)
  ↓
Recipe Resolver (P1 optional)
  ├─ current eligible Recipe
  │    → Capability/currentness validation
  │    → deterministic ActionPlan
  └─ miss / stale / inapplicable
       ↓
Capability Contract Resolution            (Shun authority)
  ↓
Provider discovery + Environment facts    (Shun authority)
  ↓
Provider × Environment bindings
  ↓
Trust / policy / feasibility hard gates
  ↓
Ranking + explicit escalation
  ↓
Action Plan
  ↓
Safety Gate / Approval or Durable Policy
  ↓
Authorized Action
  ↓
Execution Backend
  ↓
Semantic Verifier
  ↓
Lifecycle / Evidence State
  ↓
optional Recipe promotion evidence (P1)
```

A repeated task is therefore not required to re-enter fresh LLM planning. A Recipe hit is only a planning/execution fast path; it still re-enters ordinary Capability, currentness, safety, authorization and verification authority.

Three ecosystem projects are integrated only behind stable Shun-owned seams:

1. **DomainHarness** — reference durable workflow/effect-recovery backend for the fixed Shun task lifecycle. It does not own Goal interpretation, Provider ranking, AI routing, or Shun business state.
2. **AI Runtime** — optional `PlannerPort` backend for bounded structured AI Operations. It is not a workflow engine or mutation authority and is not a mandatory dependency for deterministic/structured P0 paths.
3. **runx / ECF** — P1 remote `EnvironmentBackend` for headless, job-shaped workloads. It does not define P0 local Windows execution and is not a generic desktop/session backend.

No ecosystem dependency is allowed to redefine the frozen Capability contracts or user-observable safety/verification semantics.

Current runx main is Job-first. `JobSpec` has a clear start/end, immutable runtime reference, explicit side-effect class and Process/Docker/Containerd-oriented worker execution. Its placement layer chooses fixed-pool or elastic compute and records placement evidence.

**L2 consequence:** runx is compatible with P1 remote headless jobs, but it is not the P0 local Windows desktop/session executor. Shun must define its own `EnvironmentBackend` contract and adapt ECF only for compatible job-shaped actions.

### 4.6 Authorization

An execution backend accepts only an `AuthorizedAction` produced by the central Action Controller.

```ts
AuthorizedAction {
  taskId
  actionId
  planHash
  policySnapshotRevision
  authorizationKind   // automatic | explicit-approval | durable-policy
  authorizationRef
  expiresAt?
  action
}
```

For R2/R3, authorization is bound to the exact plan hash. Editing a destructive plan invalidates previous approval.

#### 4.6.1 AuthorizationGrant / AuthorizationAuthority — privileged-side verification (closes P0-AUTH-01)

The privileged boundary MUST NOT treat an execution request as authorized merely because the caller-supplied envelope is internally self-consistent. A self-declared approval JSON attached by the caller is **not** authorization. Authorization is a verifiable grant issued by a trusted authority:

```ts
AuthorizationAuthority {
  authorityId            // Shun Action Controller approval authority
  authorityRevision
  // issues durable, integrity-protected AuthorizationGrant records in ShunStore
}

AuthorizationGrant {
  grantId
  issuer                 // authorityId + authorityRevision
  taskId
  planHash               // exact approved plan identity
  policySnapshotRevision
  actionScope            // actionId/op + declared filesystem/network/registry scope + privilege level
  issuedAt
  expiresAt
}
```

Rules:

- every `AuthorizedAction` carries a grant issued by this authority regardless of `authorizationKind` — automatic grants are issued under durable policy, explicit-approval grants additionally reference the durable approval record; the privileged boundary verifies the grant the same way in all cases;
- the grant binds the **exact `planHash`, policy snapshot revision, expiry, and action scope**; any of them changing voids the grant;
- the privileged executor validates the grant **independently**: re-derives the plan hash from the received plan, and checks grant authenticity (authority-issued and integrity-protected; the exact mechanism — signing/MAC/trusted local channel — is an L3 implementation freedom), issuer revision, policy revision, expiry, and declared scope against the received action;
- forged or self-declared `authorizationRef`s MUST be structurally refused before any side effect (demonstrated: U-06 D4-5 expired approval, D4-6 forged approvalId, D2-b post-approval plan tamper refused inside the elevated helper itself);
- **the elevated helper executable is pinned infrastructure**: its identity (hash/signature) and revision are recorded by Shun authority, and only the pinned helper is launched. Provider definitions, Planner proposals, Recipes, and bindings MUST NOT select, substitute, or parameterize the helper executable path. A helper identity/revision change is an explicit authority event recorded in the policy/identity snapshot, never an incidental runtime choice.

## 5. Task lifecycle and DomainHarness boundary

### 5.1 Shun workflow

The reference task workflow is finite and explicit:

```text
RECEIVED
→ INTERPRETING
→ CLARIFICATION? ──► INTERPRETING
→ RESOLVING
→ PLANNED
→ AWAITING_AUTHORIZATION?
→ EXECUTING
→ VERIFYING
→ LIFECYCLE_RECONCILIATION
→ SUCCEEDED | FAILED | CANCELLED | NEEDS_INTERVENTION
```

This is not an autonomous open-ended agent loop.

### 5.2 WorkflowKernelPort

Shun core depends on a narrow `WorkflowKernelPort`:

```ts
WorkflowKernelPort {
  open(task)
  send(message)
  query(taskId)
  subscribe(taskId, callback)
  recover(taskId)
}
```

The reference adapter uses released DomainHarness durable Runtime semantics.

### 5.3 DomainHarness ownership

DomainHarness may own:

- durable workflow-instance mechanics;
- serialized state transitions;
- durable acceptance/disposition of Shun workflow messages;
- effect invocation/recovery mechanics;
- workflow observation/subscription.

DomainHarness MUST NOT own:

- natural-language Goal semantics;
- Capability Registry;
- Provider Registry/ranking;
- trust/provenance decisions;
- AI model routing;
- Shun lifecycle/provenance business records;
- user authorization policy.

A fixed Shun workflow package is compiled at build time. Dynamic goals/providers are runtime data, not dynamically generated workflow definitions.

### 5.4 Store separation

- DomainHarness RuntimeStore: orchestration mechanics only.
- ShunStore: Product/business authority such as task goal, selected binding, policy/approval records, Provider/lifecycle state, execution/verification evidence.

There is no cross-database atomic transaction requirement.

All workflow-triggered ShunStore mutations use an explicit **idempotent application-effect protocol**:

```text
workflow step
→ stable effectId + intended mutation
→ DomainHarness durable effect journal
→ ShunStore idempotent apply(effectId, mutation)
→ durable application receipt
→ workflow transition/continuation
```

Rules:

- ShunStore persists the `effectId` with the authoritative mutation result;
- retrying the same `effectId` returns the recorded result rather than re-applying the mutation;
- an interrupted/uncertain call is retried/reconciled from the durable effect journal;
- the workflow MUST NOT treat an application-state mutation as committed merely because a transport call returned ambiguously;
- business truth stays in ShunStore; the DomainHarness journal proves effect/recovery mechanics, not the business fact itself.

This avoids a distributed transaction while preserving recoverable convergence between orchestration state and Shun business state.

## 6. Planner / AI Runtime boundary

### 6.1 PlannerPort

```ts
PlannerPort {
  interpretGoal(input) -> GoalProposal
  decomposeGoal?(input) -> CapabilityGraphProposal
  explainResolution?(input) -> UserExplanation
}
```

Planner output is always proposal/data.

It cannot:

- invoke Provider adapters;
- create `AuthorizedAction`;
- approve its own plan;
- mutate trust facts;
- claim task success;
- modify DomainHarness engine state directly.

### 6.2 AI Runtime adapter

An AI Runtime adapter MAY use bounded `OperationRequest` with JSON-schema validation and operation idempotency.

Shun remains responsible for:

- Product Capability validation;
- trust/policy;
- Provider/environment resolution;
- action authorization;
- semantic verification;
- user-visible success.

### 6.3 P0 dependency posture

AI Runtime is **replaceable**, not a mandatory P0 infrastructure dependency.

A structured/direct invocation of an already known Capability may bypass model use. If natural-language interpretation is required and no Planner is available, Shun returns a typed unavailable/clarification disposition rather than fabricating a plan.

A remote PlannerPort call is an **external-model disclosure** for Product privacy purposes. Under a local-only policy, a remote AI Runtime/provider is ineligible. If no local/deterministic interpreter can resolve the goal, Shun returns a typed planner-unavailable/clarification outcome rather than silently relaxing the policy.

### 6.4 Progressive Determinization — reason once, replay deterministically when safe

Shun MUST NOT treat fresh LLM planning as the default execution path for behavior that has already become stable, parameterizable, current, and verifiably repeatable.

Architecture preference:

```text
L0 — Verified deterministic Recipe
     currentness check → bind parameters → authorize → execute → verify

L1 — Known Capability + known Provider/Environment
     deterministic resolver/planner fills bounded parameters → execute → verify

L2 — Novel / ambiguous / drifted task
     PlannerPort / LLM interpretation and decomposition
     → deterministic validation/resolution
     → execute → verify
```

The runtime SHOULD choose the **lowest layer that can satisfy the frozen Capability contract with current evidence**.

Fresh LLM planning is re-entered when, for example:

- no eligible Recipe exists;
- Recipe currentness fails;
- Provider/version/environment assumptions drift;
- input/constraints are outside the Recipe applicability predicate;
- semantic verification fails;
- the user materially changes the goal;
- policy/trust state changed;
- execution enters an unresolved failure/ambiguity state.

This preserves the Product rule that reusable Recipe promotion is conditional P1: **P0 does not require automatic promotion**, but the v0.1 architecture must not make repeated tasks permanently dependent on fresh model reasoning.

### 6.5 Recipe is a verified execution asset, not just a script

A promoted Recipe is a versioned deterministic execution asset:

```ts
RecipeDefinition {
  recipeId
  revision
  capabilityId
  capabilityRevisionRange
  applicabilityPredicate
  parameterSchema
  providerBindingConstraints
  environmentRequirements
  policyRequirements
  riskFloor
  actionTemplate
  verifierId
  verifierRevision
  recoveryTemplate
  currentnessInputs
  provenance
}
```

A Recipe MAY compile to:

- parameterized CLI/API calls;
- reviewed PowerShell/Python/script templates;
- a multi-tool DAG;
- a DomainHarness subworkflow;
- a Provider-specific adapter invocation;
- another deterministic executable representation.

The representation is not the authority. The Recipe contract is.

### 6.6 Promotion gate

A successful execution does not automatically become a Recipe.

Promotion requires evidence that:

1. the Capability contract and outcome are known;
2. the successful plan can be parameterized without retaining incidental user-specific state;
3. side effects/risk and authorization semantics remain explicit;
4. semantic verification can be replayed deterministically;
5. Provider/environment/version dependencies are captured;
6. recovery behavior is defined for the promoted path;
7. currentness inputs are sufficient to reject stale replay.

Promotion may be automatic only under a future policy that itself satisfies these gates; otherwise it is explicit/system-managed P1 behavior.

### 6.7 Replay/currentness rule

A Recipe hit is not authority to execute stale behavior.

```text
Recipe match
→ currentness check
→ Capability/Provider/Environment/Policy compatibility
→ build fresh ActionPlan from the versioned Recipe
→ ordinary safety authorization
→ deterministic execution
→ semantic verification
```

Recipe replay never bypasses:

- fresh risk classification: `riskFloor` is only a lower bound captured from promotion evidence; instantiated actions may be classified at a higher risk under current inputs/policy;
- trust/provenance gates;
- current policy;
- R2/R3 approval semantics;
- Provider/environment feasibility;
- semantic verification.

If any required currentness fact is UNKNOWN, replay fails closed to the higher planning layer rather than guessing.

### 6.8 Learning boundary

Shun may learn from verified task history, but there is a strict distinction:

```text
evidence accumulation
≠ automatic Product contract change
≠ automatic trust promotion
≠ automatic arbitrary-code generation
```

Observed history may improve:

- Recipe hit confidence;
- Provider reliability evidence;
- ranking calibration;
- suggestions to promote or retire a Recipe.

It MUST NOT silently broaden Capability semantics or make unverified dynamic code durable execution authority.

### 6.9 RecipeResolverPort and lifecycle

```ts
RecipeResolverPort {
  match(normalizedIntent, objects, constraints) -> RecipeCandidates
  checkCurrentness(recipe, currentFacts) -> CURRENT | STALE | INAPPLICABLE | UNKNOWN
  instantiate(recipe, parameters, currentFacts) -> ActionPlanProposal
}
```

Recipe lifecycle is explicit:

```text
CANDIDATE
→ ACTIVE
→ QUARANTINED?
→ ACTIVE | RETIRED
```

- `CANDIDATE`: promotion evidence exists but replay authority has not been granted.
- `ACTIVE`: may be selected by the Recipe Resolver when applicability/currentness pass.
- `QUARANTINED`: verification/currentness regression disables automatic replay while evidence is investigated.
- `RETIRED`: retained for audit/history but never selected.

A failed semantic verification on an ACTIVE Recipe MUST at minimum quarantine the affected Recipe/applicability scope until an explicit disposition is recorded.

Recipe selection may bypass fresh **planning**, but not frozen Product gates.

## 7. Provider Registry / Resolver architecture

### 7.1 Registry layers

The resolver consumes three fact classes:

1. **Curated Provider facts** — shipped/versioned capability bindings, known acquisition sources, interface class, static platform requirements.
2. **Observed machine facts** — installed versions, paths, signatures, package-manager inventory, current environment capabilities.
3. **Outcome evidence** — observed task success/failure, latency, resource use, verifier results.

Trust/provenance is never inferred solely from outcome evidence.

### 7.2 Ranking policy

Hard gates execute before ranking:

```text
Capability fit
Trust / supply-chain policy
Provider × Environment feasibility
User / organization policy
Required safety constraints
```

Ranking weights are versioned data:

```text
rankingPolicyRevision
score components
penalties
candidate evidence
selected reason
```

The v0.1 percentages remain experimental.

For P0, ranking MAY be implemented as a small deterministic rule set rather than a weighted score when the benchmark shows equivalent or better decisions. The frozen requirement is **hard gates + explainable selection + explicit no-feasible-binding/escalation**, not a mathematically complex scorer.

When a Capability is satisfied by exactly one trusted native/platform binding (for example an OS observation API in Loop C), the resolver may select it directly after hard gates. It MUST NOT manufacture artificial Provider competition merely to exercise ranking.

Risk is not silently added as another score. If a candidate requires risk escalation that is disallowed by current policy, it is rejected. If escalation is allowed, that fact is explicit in the returned resolution and later ActionPlan.

### 7.3 Provider learning

Observed reliability MAY update a local evidence profile after verified outcomes.

Automatic learning MUST NOT:

- change provenance/trust authority;
- broaden declared capability coverage;
- weaken policy gates;
- change a frozen Capability contract.

## 8. Execution backends

### 8.1 EnvironmentBackend

```ts
EnvironmentBackend {
  observe() -> EnvironmentFacts
  canPrepare(requirements) -> Feasibility
  prepare(binding) -> PreparedEnvironment
  execute(AuthorizedAction) -> ExecutionReceipt
  cancel(actionId)
  cleanup(preparedEnvironment)
}
```

### 8.2 LocalWindowsBackend — P0

P0 local execution surface is intentionally pragmatic:

- filesystem/process APIs;
- structured subprocess execution;
- PowerShell for Windows management APIs where it is the stable machine interface;
- winget / official package mechanisms for supported acquisition;
- WMI/CIM/EventLog/performance APIs for observation;
- existing Provider CLI/library/API adapters;
- semantic UI / vision only through explicit fallback interfaces, never hidden inside the structured executor.

Elevation is not allowed to be an ad-hoc Provider behavior. Elevated execution must remain behind the same `AuthorizedAction` boundary.

#### 8.2.1 Elevation seam disposition — U-06 PASS (frozen)

**ONE_SHOT_ELEVATED_HELPER_SUFFICIENT.** A persistent privileged broker is **not** required at P0.

Evidence: Issue #5 terminal; demo commit `bfba92e5493537198e07cc4480f8f040ebeadfcd`, 22/22 PASS on real Windows 11 25H2 build 10.0.26200.9457 with UAC fully enforced (`EnableLUA=1`, `ConsentPromptBehaviorAdmin=5`, `PromptOnSecureDesktop=1`) and a filtered (non-elevated) admin token. The elevation-gated fixtures were proven genuine on the host (`C:\Windows` / `HKLM` writes denied), and no unattended elevation side channel exists there (`Register-ScheduledTask -RunLevel Highest` from the filtered token → Access Denied).

The proven one-shot contract, which `LocalWindowsBackend` MUST preserve:

- typed `AuthorizedAction` envelope passed as a JSON file on disk — never command text; no LLM prompt or arbitrary Provider object crosses the privilege boundary;
- the helper re-validates **independently inside the privileged boundary**: schema/op enum → planHash re-computation (independent canonicalization) → grant binding/expiry/scope per §4.6.1 → privilege consistency → phase journal → `ExecutionReceipt` → independent post-state verification;
- no listening channel, no helper reuse, no arbitrary shell endpoint (unknown-op `shell.exec` refusal is structural, not accidental);
- **cooperative cancellation + helper-side deadline**: a non-elevated parent cannot force-kill an elevated child (Access Denied), so the helper enforces its own deadline (per-step checks plus process-level `WaitForExit(timeout)` + kill) and polls a cancel sentinel between phases (`CANCELLED`); launcher-side timeout tree-kill (`TIMED_OUT`) remains last resort for non-elevated children;
- **fail-closed receipts**: every validation/execution exception produces a structured `REFUSED`/`FAILED` receipt — a crash without a receipt would break the §9.4 recovery classification (two crash paths found during the demo were hardened exactly this way before the PASS run set);
- a genuine secure-desktop UAC refusal yields structured `UAC_DECLINED` with the helper provably never started (empty journal);
- shell metacharacters in typed parameters pass through byte-exact and NTFS-illegal path characters fail closed with a structured `REFUSED` — no string-concatenated shell command exists anywhere in the design.

**Unattended elevation is a separate policy seam.** Interactive UAC consent is not automatable by Windows design (demonstrated, not assumed). The executor seam is agnostic to how elevation is obtained; any unattended-elevation channel (for example a pre-authorized elevated scheduler entry) is a policy/authorization-seam decision with its own approval/durable-policy semantics, and MUST NOT be introduced as hidden executor behavior.

**Research harness boundary.** `research/u06-harness/` at the demo SHA is throw-away evidence (its canonicalization is deliberately duplicated across the boundary to prove representation stability). It is not proposed, and MUST NOT be merged, into the production mainline; production uses one canonicalization implementation.

### 8.3 runx/ECF backend — P1

The ECF adapter is valid only when an action can be expressed as a bounded headless Job:

- clear start/end;
- immutable runtime identity;
- declared side-effect class;
- explicit artifacts;
- no dependence on an interactive desktop session.

Mapping:

```text
Shun AuthorizedAction
+ Environment requirements
→ ECF JobSpec
→ Placement / Lease / JobResult
→ Shun ExecutionReceipt
→ Shun semantic verification
```

ECF's `JobResult.Completed` is execution evidence, not Shun task success.

Interactive Windows desktop/UI tasks do not map to ECF v0.2 JobSpec and must not be forced through it.

## 9. Side-effect and safety model

### 9.1 Central Action Controller

Provider adapters and Recipes produce **plan proposals**, never raw execution authority.

The Action Controller recomputes the effective risk classification from the instantiated action, current objects/environment and current policy. Historical Recipe metadata can set a risk floor but can never lower the current classification.

```text
Provider adapter
→ proposed ActionPlan
→ policy/risk classification
→ plan/preview
→ checkpoint or recovery disposition
→ approval/durable-policy if required
→ AuthorizedAction
→ ExecutionBroker
→ receipt
→ verifier
```

### 9.2 Risk classes

- R0 — read-only / no side effect: automatic when policy allows.
- R1 — reversible bounded write: may be automatic under policy; verification required.
- R2 — destructive/potentially harmful: plan + preview + recovery disposition + explicit approval or sufficiently specific durable policy + verification. Until Product semantics explicitly narrow it, bulk move/rename, uninstall/removal, and other operations that can materially disrupt user organization/state use the conservative R2 interpretation even when a technical rollback may exist.
- R3 — high-impact/difficult-to-reverse: explicit approval plus stronger backup/checkpoint requirements; P0 reference loops avoid broad R3 automation.

### 9.3 Privilege boundary

Privileged execution is an infrastructure boundary, not a Provider-scoring property.

The privileged executor receives no LLM prompt and no arbitrary Provider object. It receives only a validated `AuthorizedAction` envelope whose plan hash and authorization are already fixed — and whose authorization it re-verifies against a trusted grant itself (§4.6.1), never on the caller's say-so.

### 9.4 Side-effect recovery state model (closes P0-RECOVERY-01)

Every side-effecting action carries exactly one durable recovery classification, derived ONLY from the privileged phase journal plus independent post-state verification — never from transport/exit optimism:

```text
NOT_STARTED                  — no RECEIVED in the journal / helper provably never started (e.g. UAC_DECLINED, empty journal)
FAILED_BEFORE_EFFECT         — journal stops before the first EXEC_START (all validation phases precede any side effect)
MAY_HAVE_EXECUTED_UNCERTAIN  — interruption inside a step's [EXEC_START, EXEC_DONE) window; resolved to a concrete
                               outcome only when the action declares verifiable expected state, otherwise honestly UNCERTAIN
COMPLETED_VERIFIED           — RECEIPT_WRITTEN + independent post-state check
```

Recovery rules:

- journal replay MUST tolerate torn appends (a torn line is isolated; earlier phases stay intact);
- a `MAY_HAVE_EXECUTED_UNCERTAIN` destructive action (R2/R3) MUST NOT be blindly retried. The required order is **reconcile-first**: run the declared post-state verification/reconciliation against expected state and only then classify;
- retry is permitted only when (a) the state model proves `NOT_STARTED` / `FAILED_BEFORE_EFFECT`, or (b) the plan's recovery contract records an explicit idempotency/currentness guarantee for that exact action under current facts;
- **stable identity rule**: recovery/retry reconciles the SAME stable `actionId` (and the same stable effectId for ShunStore mutations, §5.4). Neither DomainHarness effect recovery nor workflow retry may create a NEW destructive execution under a fresh identity for an unresolved prior one — a lost receipt is a reconciliation input, not a new authorization;
- a persistent privileged broker could not shrink the uncertain window to zero either (it crashes between dispatching work and recording the outcome just the same), so the one-shot helper model of §8.2.1 loses nothing here — only the journal location differs, not the semantics.

U-06 demonstrated all four classifications from journal + post-state alone (D5, 5/5, including torn-journal replay).

## 17. Post-U06 Controller delta — P0 finding closures

The Controller delta review that consumed the U-06 terminal identified two new P0 architecture findings. Both are closed by this revision and stay open for independent confirmation:

### P0-AUTH-01 — privileged boundary must verify grant authority, not caller self-consistency

Finding: validating only the internal self-consistency of a caller-supplied approval lets a forged/self-declared JSON stand as authorization at the privileged boundary, and would let Provider/Planner influence which helper executable runs.

Closed in §4.6.1 and §8.2.1: trusted `AuthorizationAuthority` / `AuthorizationGrant` bound to exact planHash, policy snapshot revision, expiry and action scope; independent grant verification inside the privileged boundary; caller-supplied self-declared approval insufficient; helper executable identity/revision pinned by Shun authority — Provider/Planner/Recipe must never select the helper executable.

### P0-RECOVERY-01 — four-state effect recovery with reconcile-before-retry

Finding: without a durable effect-recovery classification, an interrupted side-effect action is either silently lost or blindly retried, and recovery could create a new destructive execution instead of reconciling the interrupted one.

Closed in §9.4: `NOT_STARTED` / `FAILED_BEFORE_EFFECT` / `MAY_HAVE_EXECUTED_UNCERTAIN` / `COMPLETED_VERIFIED` derived from journal + post-state only; UNCERTAIN destructive actions never blindly retried (reconcile-first); retry requires proven non-execution or an explicit idempotency/currentness guarantee; stable `actionId`/effectId reconciliation instead of new destructive executions.
