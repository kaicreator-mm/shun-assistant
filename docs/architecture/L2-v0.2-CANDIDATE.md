## 1. Architecture drivers / minimal end-user critical path

Ship a real, Windows-first, ordinary-user experience for (1) first actual LLM request and scoped system report, (2) bounded storage improvement with truthful preview and post-state, (3) selected-root file search/organization, (4) JS/TS Recipe proposal → independently verified, saved exact revision → model-free manual replay, (5) existing real Sharp/WinGet/storage flows through common UI, (6) **small launchable core** and an on-demand, allowlisted optional Provider acquisition, (7) portable Windows packaging. User-oriented errors and declines are part of each journey.

Non-goals: general-purpose model-authored shell, per-user startup mutation as mandatory P0, drivers/services/registry tweaking, full provider marketplace, app8 import, background autonomous tasks, arbitrary Python/CMD execution, general Rust/FFI gateway or Linux feature parity.

Architecture success requires a direct, demonstrably safe path from each typed user goal to independently verified results. **No “direct script to OS” route exists.**

## 3. Concrete reference components and trust boundaries

```text
Windows user | loopback UI (or packaged desktop shell)
  → Task API → Intent / Recipe index ── exact trusted Recipe → typed param rebind
                  │ cache miss / new request
                  ▼
            LLM PlannerPort proposal
       ┌── remote opt-in HTTPS ─────── secrets/egress/data policy
       └── host-managed LOCAL runner ─ independent LOCAL provenance/egress proof
                  │ untrusted proposal / script text
                  ▼
     Goal/Capability Resolver & typed approved ActionGraph
                  │
    preflight (schema, path, verifier, executable identity) + manifest/dry-run
                  ▼
          Shun ActionController
             grants, planHash, R0/R1/R2, per-effect currentness
              /                      \
 Tier 1 Node/fs+fixed CIM     optional Tier 2 reviewed Rust+napi-rs
              \                      /
                 Windows bounded effects
                  ▼
     independent semantic verifier + signed/recorded outcome receipt
                  ▼
      ShunStore / Workflow durable state
                  ▼
   user-visible result + optional immutable Recipe promotion
```

A curated on-demand Provider payload enters **only** through `TrustedProviderCatalog → Managed Acquisition → Hash+signature/dependencies+ABI verification → VerifiedProviderBinding`; it NEVER enters as a raw model-proposed URL, JS import path or authorized-action signature. Download approval and effect approval are independent.

### 3.1 LLM model host and privacy

- `PlannerPort` receives only typed, minimized `GoalProposalInput` (`goalText`, sanitized host facts, bounded permitted capability names and schemas, requested operation constraints, token/cost budget), not full arbitrary file contents, credentials or environment variables.
- Remote: OpenAI-compatible API over TLS with explicit user opt-in per disclosure/privacy policy; OS credential storage handle, bounded timeout/token ceiling, negative-path malformed JSON/provider outage, request response version envelope and data redaction. The remote adapter cannot create trusted GoalContract/ActionPlan/grant; proposal re-resolved by existing deterministic core.
- Local: one user-configured Ollama/llama.cpp-compatible inference backend sufficient at P0, but origin identity and no-external-network guarantee must be **host-enforced and falsified on Windows**. Node recognizing `127.0.0.1` or receiving a `LOCAL` enum does NOT prove locality; absent enforceable origin/egress attestation, fail closed and preserve deterministic offline native function. Windows Home/Pro profiles may choose signed isolated helper/firewall/other executable enforcement, but must be measured, not assumed.
- No local weights or optional Provider payload bundled in Core. An offline first run without configured model supports deterministic diagnostics and settings/onboarding; it must not claim that inference worked.

### 3.2 Script/Recipe exact identity and execution

`Goal → Recipe lookup → currentness` precedes a new LLM call. Only Shun-curated aliases / user-selected Recipe IDs can select model-free action automatically; vector similarity gives suggestions, not authority.

Semantic contract types (exact field names are L3 flexibility, effects and identity invariants are not):

```ts
interface VerifiedExecutableIdentity {
  recipeId: string; revision: string;
  representations: {
    kind: 'JS_SOURCE' | 'TYPED_GRAPH' | 'TRANSPILED_ARTIFACT';
    required: true;
    sha256: string;
  }[];
  canonicalDigest: string;       // includes all present representation IDs/hashes
  declaredEffectsDigest: string;
  verifierId: string; verifierRevision: string;
}
interface RecipeRunRequest {
  identity: VerifiedExecutableIdentity;
  parameters: unknown;           // checked against pinned JSON Schema
  expectedProviderBinding?: { id: string; version: string; artifactSha256: string };
  currentPolicyRevision: string;
}
```

- Immutable revision and representations: changing **any** source/graph/compiler output/declared effects/verification semantic creates **new revision** and new preflight, independent validation, user promotion and authorization. If the stored old revision changes unsolicited → BLOCK, zero side effects. `REVALIDATE` means unchanged executable identity with environment/policy drift.
- Product mode `JS_RECIPE`: **do not execute unrestricted generated JS in the main Node process**. An explicitly admitted typed action graph is always allowed to *propose* effects; JS source can be stored/inspected and transformed by reviewed parser into typed ops; any real raw JS computation needs an independently proved restricted host mechanism. PowerShell is fixed audited read-only diagnostic functions, not free-form generated `ps1`. TS is compiled to JS with pinned compiler identities, no ambient arbitrary imports.
- `EXACT_REUSE` recomputes the entire manifest digest including `JS_SOURCE`, `TYPED_GRAPH`, `TRANSPILED_ARTIFACT` when present; validates provider/runtime/currentness and fresh plan/action grant. An exact cached Recipe is **never an AuthorizationGrant**. Changed valid params force new per-run effect manifest and reauthorization; dangerous actions require correct R2 preview every run.
- Effect journals key off `taskId+actionId+planHash` and stable effect identity; restart uncertainty never retriggers unknown destructive effects. Before changing a file, verify user-selected root, reparse/junction/symlink, identity, destination collision and protected canaries. Verify actual post-state, not exit code.

### 3.3 Two system layers

- **Tier 1 mandatory:** Node.js `fs/os`, Windows system-native functions and reviewed fixed PowerShell/CIM cmdlets for read-only system inventory; typed mutation follows Shun ActionController. Fail closed on unknown OS facts; cap process enumeration, file recursion, timeouts, PII and privileged routes.
- **Tier 2 conditional:** Rust via `napi-rs`, `windows-rs` when native Win32/COM/WinRT, foreign C ABI, memory/compute-intensive workloads or performance measurement warrants. A concrete named use case must carry `WHY_NOT_NODE`, `WHY_RUST`, ABI/lifetime/threading/panic/handle tests and packaging provenance. Tier 2 may be `NOT_REQUIRED` for P0 release. No general FFI bridge, Koffi, node-win32-api, dynwinrt, node-api-dotnet.
- P0 optimization = scoped storage cleanup with independent bytes measurement, plus **read-only** startup and background task diagnosis. User-startup mutation remains P1 proof-gated, no AV/Defender/update/service/driver/registry performance “tuning”.

### 3.4 Lazy Provider architecture

- Trusted signed/pinned fixed catalog owned by Shun, key/distribution trust root exists **before** payload download. Catalog entries identify capability/binding, origin/version/size/hash/expected files/OS/arch/Node native ABI/dependencies/license, permitted installation/effect scope, verifier and removal lifecycle.
- Prefer platform installed trusted tools first; when absent `ABSENT→PENDING_CONSENT→ACQUIRING→HASH_VERIFIED→INSTALLED→READY`. `OFFLINE|TRUST_FAILED|ABI_MISMATCH|STALE|RECOVER_UNCERTAIN|REMOVED` are explicit results. Stage into Shun-owned root then atomically activate with journal; no arbitrary DLL search or dynamic JS/npm install from model.
- `sharp` Node-native payload compatibility and v0.1 managed portable JIT semantics are distinct. Exact signed module loader in bounded child worker and native ABI/restart failure are **new** host-dependent obligations. v0.2 does not need in-process hot code swap. Installed Windows WinGet can be reused by signed source binding when present; **not** silently embedded in Core.
- Existing user-owned data and PATH programs are not reclassified as provider-owned because a basename matches. On remove, protected file identities, leases/in-use state and source-created outputs are preserved; trust revocation blocks reuse; Recipe Provider pins force revalidation or no run.

### 3.5 User interface and distribution

- Reuse existing loopback-only Control API/approval read models, preserving strict Host+Origin+CSRF equivalent and no grant issuance via UI. Make app default a **real** host-backed UI; preserve `DEMO` as explicitly labeled opt-in validation mode only.
- User flow: onboarding model selection/LLM disclosure + trusted workspace, natural-language typed goal, observations and clarification, concrete preview/risk/permissions (file roots, bytes, software to acquire), start/progress/cancel and verified receipts, Recipe store/enable/disable/replay, accessible errors. Distinguish `SIMULATED`, `DRY_RUN`, `EXECUTED`, `VERIFIED`, `BLOCKED`, `UNCERTAIN`.
- Package Windows 11 Home/Pro x64 as portable one-step launch, pinned Node/core, no pnpm/dev toolchain or mandatory admin. Native diagnostics and bounded storage operate offline even with missing provider/model. Runtime/installers/manifest published with SHA/OS/arch proof; repair/remove cannot delete user files.
