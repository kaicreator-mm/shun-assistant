# L2 v0.2 Delta — T04 Bounded One-Shot Privileged Trusted Writer + Elevated-Only Durable Anchor Root

Status: DELTA PROPOSAL (v0.2 relative to frozen `L2-v0.1.md`) — authored per the
Controller adjudication on Issue #37 (SHUN_T04_C06_PROTECTED_TRUST_PRINCIPAL_
ARCHITECTURE_R0 → repair round R3). **This document does not modify the frozen
L2 v0.1**; where it reuses v0.1 records it quotes them. It names the components,
clarifies the anchor-root semantics, and fixes the pre-issuance vocabulary so
the implementation work in `packages/executor-windows` has a stable target.

Adjudication constraints (binding):

- bounded ONE-SHOT privileged trusted writer — every issuance is one elevated
  process that applies one approved job and exits;
- **NO resident service** (no listening channel, no daemon, no background
  authority process of any kind);
- **NO same-user ACL theater** (no protection claim rests on ACLs the same
  user can rewrite; owner-implicit rights are explicitly not protection);
- explicit approval before every issuance; fail-closed interim behavior while
  the anchor root is not yet elevated-only.

---

## 1. Problem restatement (why v0.1's mechanism cannot close C06)

L2 v0.1 §4.6.1 makes grant authenticity + currentness a privileged-side
verification duty and pins the helper as infrastructure. T04 implemented that
with an HMAC scheme (`GrantIntegrity = HMAC_SHA256(key, canonical(grant))`)
whose key lives in the authority store (`grant-hmac.key`). Under HMAC, any
principal able to VERIFY is also able to SIGN: the runtime user must verify,
so the runtime user can forge — the same-user attacker chain (replace key →
re-sign grant → rewrite currentness → present forged envelope) is structural,
not a bug. The live negative record
`test/authority-same-user-known-open.test.ts` runs this exact recipe every
suite and fails as predicted. Externalizing the key to a protected path helps
only where the READER is elevated; it does not make the runtime principal a
non-signer.

Conclusion: closing C06 requires changing WHO WRITES the authorization
records — a trust principal the same-user attacker does not control — not
stronger verification by the principal being attacked.

## 2. Named component: `ShunAnchorWriter` (one-shot privileged trusted writer)

**Component name: `ShunAnchorWriter`** (package `@shun/executor-windows`,
module `src/authority-writer/`). Responsibilities and non-responsibilities:

Owns (is the ONLY writer of, once deployed on the anchor root):

1. grant issuance — writing `AuthorizationGrant` records (L2 v0.1 §4.6.1
   shape, unmodified) into `<anchorRoot>/grants/`;
2. currentness — writing `current-authority.json` (issue/rotate/revoke,
   L2 v0.1 §4.6.1 currentness semantics, unmodified);
3. key custody + rotation — the grant-integrity key material, held OUTSIDE
   same-user reach (see §3);
4. pin updates — `helper-pin.json` / `system-tools-pin.json` / writer-pin
   (§5), always at an explicit authority event.

Does NOT:

- execute actions (that stays with the pinned one-shot helper, L2 v0.1 §8.2.1);
- decide what is authorized (issuance is driven by approved jobs, §6);
- stay resident, listen, poll, or accept runtime requests: the writer runs
  ONLY as `anchor-writer.mjs <jobFile> <receiptFile>` — a fresh elevated
  process per job, applied then exit. Its entire writable surface is the
  anchor root; it accepts no network, no pipe, no reused process.

Process integrity: the launcher measures the writer bundle's sha256 against
the writer-pin BEFORE requesting elevation (same N-2 pattern as the action
program pin); the elevated writer re-measures its own bytes against the same
pin pre-write and refuses on any mismatch. The interpreter is pinned like the
helper's (C12 pattern).

## 3. Clarification: the authorization anchor root is the write-protection substrate of ShunStore authorization records

**Authorization anchor root (`<anchorRoot>`)** := the directory on which the
ShunStore authorization records named in §2 are stored, and the ONLY location
whose writer is `ShunAnchorWriter`. "Authorization records" = the set L2 v0.1
§4.6.1 + T04 already define: grants, current-authority.json, the integrity key
material, and the pin records. The anchor root is the SUBSTRATE that makes
those records durable and write-protected — the records remain byte-compatible
with the frozen T00 schemas; what changes is which principal can persist them.

Deployment shape (the only shape counted as protected):

- the anchor root is created by an elevated provisioning step and its DACL
  grants write (create/append/modify/delete) to **Administrators and SYSTEM
  only**; the runtime user's token — filtered or standard — has read
  (and only read) on the record set;
- the grant-integrity key file additionally denies READ to the runtime user:
  key-bearing verification happens only inside elevated principals — the
  writer at apply time, and the (already-pinned, already-elevated) helper for
  its privileged-side grant verification per L2 v0.1 §4.6.1 — while the
  runtime user consumes pre-issued, already-integrity-protected grants (§6)
  without ever needing the key. A principal that cannot read the key cannot
  sign; under HMAC that is the whole game.
- every ACL on the anchor root is owned by Administrators/SYSTEM. Any
  protection expressible only through an ACE the runtime user could rewrite
  (owner rights) is **not** a recognized deployment shape and is not claimed
  as protection anywhere in this delta (no theater clause).

Honest interim (until a host is provisioned this way): the launcher-side
interim fail-closed default shipped in this same round
(`src/anchor-protection.ts`, refusal code `ANCHOR_FORGEABLE_SAME_USER`) probes
same-user writability with real access attempts and refuses privileged side
effects when any anchor is writable. That gate is the transitional stance, not
the architecture.

## 4. What "elevated-only durable anchor root" means for the trust argument

After deployment, the in-model attacker (same user, no admin token, per the
C06 threat statement) can no longer:

- write grants / currentness / pins (no write on the anchor root);
- read or replace the integrity key (no read on the key file);
- mint grants by any other route: signing requires the key; writing records
  requires the anchor root; the writer itself only applies approved jobs.

Therefore the 5-step same-user recipe dies at step 1 (key write), step 2
(signing — key unreadable), and step 3 (currentness rewrite) — each refusal is
OS-enforced on the substrate, not verified-into-existence by code the attacker
influences. The known-open record stays live and becomes the regression signal:
if any step starts succeeding against a properly provisioned root, the recipe
assertions flip red.

Residuals declared up front (documented, not hidden):

- an attacker WITH admin is out of model (L2 v0.1 §4.6.1 threat basis);
- TOCTOU between the runtime's read of a record and the writer's next write is
  bounded by the writer's single-writer discipline and the existing
  currentness re-check inside the privileged helper immediately pre-effect;
- availability, not integrity: an attacker can still deny service (they always
  could); denial is not forgery.

## 5. Bootstrap and the writer-pin (the honest chicken-and-egg)

The writer-pin cannot live inside a store the writer has not yet protected.
Bootstrap is a one-time elevated provisioning sequence (an authority event,
never a runtime decision):

1. elevated provisioning creates `<anchorRoot>` with the §3 DACLs;
2. it copies/creates the record set (existing store migrated, or fresh);
3. it provisions `writer-pin.json` INSIDE the anchor root measuring the
   writer bundle + interpreter bytes, at the same trusted moment as the
   helper-pin (same trust semantics as L2 v0.1 §4.6.1 "pinned
   infrastructure");
4. the runtime configuration is pointed at `<anchorRoot>` (executor
   `authorityDir`), and the old co-located store is retired (moved/deleted) so
   a stale writable copy cannot be re-presented as the anchor.

After bootstrap, every writer launch re-verifies its own bytes against the
root-internal writer-pin inside the elevated boundary. A writer byte change is
an authority event (re-pin), mirroring the helper's rules verbatim.

## 6. Policy-window pre-issuance semantics

The runtime NEVER asks the writer for authorization at execution time (no
resident service). Authorization reaches the runtime exclusively as **pre-
issued grants**:

- **Policy window**: a time-bounded issuance authorization
  `{ windowId, notBefore, notAfter, policySnapshotRevision, authorityRevision,
  scopeBudget }` approved out-of-band (operator/policy gate — the L2 v0.1 §3.1
  chain ends in an explicit approval artifact). A window is an issuance
  license, NOT a grant: nothing executes on a window alone.
- **Writer job**: one issuance order
  `{ jobId, jobType: 'issue-grant' | 'revoke' | 'rotate-key' | 're-pin',
  policyWindowRef, payload, notBefore, notAfter }`, integrity-protected by the
  anchor key. `applyJob` accepts a job only when:
  1. job integrity verifies against the anchor key (writer-only readable);
  2. the referenced policy window is CURRENT at apply time (revision matches
     `current-authority.json`, clock inside `[notBefore, notAfter]`);
  3. the job's `payload` falls inside the window's `scopeBudget`;
  4. the job is not already consumed (write-ahead consumption ledger, §7);
  5. the writer's own byte pin verified (§5).
- **Pre-issuance**: approval flow = approve window → (immediately or later)
  writer applies jobs minting the actual `AuthorizationGrant`s → runtime
  executes against pre-issued grants exactly as L2 v0.1 §4.6 already demands
  (grant + currentness + expiry + scope, verified privileged-side). Because
  grants are pre-issued under a window whose revision the writer checked, a
  grant can never outlive its policy basis: revocation is a writer currentness
  write; window expiry stops future issuance without touching outstanding
  grants (their own `expiresAt` and currentness still govern execution).
- The runtime request path therefore contains no minting authority AT ALL —
  the property that removes the runtime user from the signing position.

## 7. Write semantics (one-shot, atomic, crash-honest)

Per job the elevated writer performs exactly one transaction:

1. write-ahead consumption: append `jobId` to the consumed-jobs ledger
   (durable temp+fsync+rename inside `<anchorRoot>/jobs/ledger/`); a crash
   after this point leaves the job consumed-but-unapplied — fail-safe (no
   effect), surfaced honestly in the receipt as `CONSUMED_NOT_APPLIED`;
2. payload write: record file assembled in a temp file, fsync, atomic rename
   into place (grant records / current-authority.json / pin files). A crash
   before the rename leaves the anchor untouched — no partial anchor state
   ever exists;
3. receipt: structured job receipt written to the operator-supplied path,
   then process exit. One job per process; a second job requires a second
   consent.

Replay of a consumed `jobId` is refused before any write regardless of job
validity. Ledger append and payload write are separate crash points by design;
both fail toward "no effect" and both are visible in the receipt/journal
channel.

## 8. In-scope implementation state (this round) and split boundary

Landed in this repair round (bounded by the frozen T00 schema + single-package
write set, unattended-validated):

- `src/authority-writer/` core: job schema + integrity, policy-window checks,
  write-ahead consumption ledger with replay refusal, atomic temp+fsync+rename
  payload writes, writer identity (bytes-pin) verification — with real-Windows
  negative controls (forged job refused; consumed-job replay refused; injected
  crash between temp write and rename leaves the anchor untouched; user write
  DENIED on the anchor root → apply fails with nothing written).
- Interim fail-closed default (§3 honest interim) in the privileged launcher.

Split out (prerequisites beyond frozen T04 authority — NOT claimed done):

- the elevated provisioning step (§5) and the real UAC-consented writer
  launch: requires interactive consent; PENDING_INTERACTIVE, never claimed
  validated;
- the writer entry's end-to-end positive path on a real elevated host
  (negative/denial paths are unattended-validated; the positive path is not);
- executor/runtime wiring to consume anchor-root deployments end-to-end.

C06 status vocabulary for this round: **INTERIM_FAIL_CLOSED +
IMPLEMENTED_PENDING_HOST_VALIDATION** (bounded core landed, negatives green;
architecture NOT closed; UAC positive path pending interactive validation).

## 9. Freeze compatibility

- No contract schema changes: grants, current-authority, pins keep their
  frozen T00/L2 v0.1 shapes; the writer writes the SAME record bytes the
  trusted-store module already defines.
- L2 v0.1 §3.1 authority rule is strengthened, never bypassed: windows and
  jobs are new approval artifacts UPSTREAM of issuance, and every executable
  action still flows the full v0.1 chain.
- The helper stays the only action executor; the writer never executes actions.
